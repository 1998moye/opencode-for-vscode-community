# OpenCode for VS Code — 社区版产品需求文档

**实现跟踪**（状态、v1/v2 裁剪、下一里程碑）：[ROADMAP](../../.scratch/opencode-for-vscode/ROADMAP.md) · [issues 任务单](../../.scratch/opencode-for-vscode/issues/)

## 问题陈述

OpenCode 官方 VS Code 扩展主要把终端用户界面带入编辑器，用户仍需面对终端式交互、快捷键冲突、上下文添加不直观、权限确认分散、文件变更不易审查等问题。希望使用 OpenCode 命令行程序的开发者，缺少一个像 Codex 或 Claude Code VS Code 扩展一样的原生图形客户端：它应完整复用 OpenCode 的模型、智能体、会话、权限、命令、工具和配置能力，同时充分利用 VS Code 的编辑器上下文、差异查看、通知、远程开发和主题系统。

目标用户准备自行安装、认证和维护 OpenCode 命令行程序，但希望日常编码工作全部在插件中完成，而不是频繁返回外部终端。产品还必须适合公开发布：跨平台、安全、可审计、可访问、可诊断，并能够应对 OpenCode 程序接口持续演进。

## 解决方案

构建开源的 **OpenCode for VS Code — 社区版**：一个面向 VS Code 桌面版的非官方 OpenCode 原生客户端。

插件由扩展后端启动或连接 `opencode serve`，通过官方 TypeScript 开发工具包调用 OpenCode 服务接口，并通过服务器推送事件接收会话、消息、工具、权限、子智能体和状态变化。OpenCode 始终是会话、Provider 凭据、权限与原始文件差异的事实来源；插件负责连接安全、视图状态、工作区写入仲裁，以及基于 OpenCode `FileDiff` 和当前磁盘内容完成安全的逐文件审查。插件不建立第二套聊天历史或文件快照数据库。

产品提供活动栏侧边栏和编辑器标签页两种聊天形态、全局互通的会话管理、并发任务、动态模型供应商认证、模型与智能体选择、完整命令与提及、折叠式思考和工具时间线、精细授权、文件变更审查、附件、内置交互终端、模型上下文协议与配置管理，以及远程安全外壳、Linux 子系统和开发容器支持。

产品以天蓝色为品牌主色，同时遵循 VS Code 主题、高对比度和键盘交互规范。开发期间通过本地扩展安装包持续自用和修复，达到完整性与稳定性目标后再发布到 VS Code 应用市场。

### 术语说明

- CLI：命令行程序。
- API：程序接口。
- SDK：开发工具包。
- SSE：服务器向客户端持续推送事件的机制。
- Extension Host：VS Code 扩展后端，负责执行可信代码。
- Webview：插件内的网页视图，只负责展示和用户操作。
- Provider：模型供应商。
- Agent：智能体。
- Diff：文件变更差异。
- Snapshot：文件快照。
- PTY：可接收用户输入的伪终端。
- MCP：模型上下文协议。
- 连接配置：描述 OpenCode Server 地址、所有权、传输安全、文件系统关系和能力限制的配置。
- 跟随模式：会话已处于运行状态时，只接收状态和事件、不再发送驱动操作的客户端状态。
- 三方合并：以 Agent 修改前内容、Agent 修改后内容和当前磁盘内容判断可安全回退部分与冲突部分。

## 用户故事

### 安装、启动与连接

1. 作为首次安装插件的用户，我希望插件自动检测 OpenCode CLI，从而无需手动填写常见安装路径。
2. 作为使用自定义安装位置的用户，我希望配置 OpenCode 可执行文件路径，从而可以继续使用自己的工具链布局。
3. 作为 CLI 版本过旧的用户，我希望看到明确的最低版本与升级提示，从而知道为什么某项能力不可用。
4. 作为 CLI 版本较新的用户，我希望插件按 API 能力降级，从而不会因单个不兼容功能导致整个聊天不可用。
5. 作为普通用户，我希望插件默认安全地启动本机 OpenCode 服务，从而无需理解端口和服务进程。
6. 作为高级用户，我希望通过明确标识文件系统关系和安全级别的连接配置接入已有 OpenCode Server，从而在不误用本地路径或泄露凭据的前提下复用服务实例。
7. 作为安全敏感用户，我希望插件启动的服务仅监听本地随机端口并启用随机认证，从而避免其他进程或网络用户接管 Agent。
8. 作为关闭 VS Code 的用户，我希望由当前窗口发起的任务先请求中止、由插件启动的服务和终端随后被终止，同时不误杀用户自行管理的外部服务，从而不会留下失控进程或破坏其他客户端。
9. 作为再次打开 VS Code 的用户，我希望选择此前中断的会话并手动继续，从而保留上下文且不会自动产生费用或执行命令。
10. 作为没有打开文件夹的用户，我希望浏览和继续历史会话，并在新建编码会话前选择初始目录，从而不会默认暴露整个用户主目录。

### 会话与任务

11. 作为同时使用 CLI、桌面端和 VS Code 的用户，我希望所有 OpenCode 会话互通，从而可以在不同客户端间无缝继续工作。
12. 作为长期用户，我希望会话列表直接来自 OpenCode，从而不会遇到插件数据库与 CLI 数据不一致。
13. 作为多项目开发者，我希望会话在界面中全局可见且可自由切换，从而不受当前 VS Code 工作区的人为分组限制。
14. 作为新建会话的用户，我希望插件以当前活动文件所属工作区作为不可被界面切换悄悄改变的初始工作目录，从而获得稳定的相对路径、项目配置和请求路由。
15. 作为跨目录工作的用户，我希望跨目录访问继续使用 OpenCode 的外部目录权限，从而在保持会话自由的同时维持安全边界。
16. 作为专注单一任务的用户，我希望当前窗口一次只运行一个由插件发起的会话，从而避免同时修改同一项目带来的混乱。
17. 作为切换会话的用户，我希望插件在切换前中断当前窗口发起且仍在运行的会话，从而明确停止旧任务后再继续新任务。
18. 作为执行任务的用户，我希望统一看到运行、跟随、等待授权、完成和失败状态，从而快速判断需要关注的会话。
19. 作为在多个客户端打开同一会话的用户，我希望其他客户端正在运行时进入只读跟随模式，从而不重复驱动同一会话，也不虚假承诺全局锁定。
20. 作为管理历史的用户，我希望新建、重命名、删除和筛选会话，并且仅在主动点击“新建会话”时创建会话，从而保持会话列表清晰。
21. 作为修改历史提问的用户，我希望重新发送或编辑旧消息时仍在当前会话中追加一条新消息，而不是创建分支或覆盖原历史，从而保留可追溯记录并避免会话数量膨胀。
22. 作为需要协作的用户，我希望生成和取消 OpenCode 原生分享链接，从而可以分享会话结果。
23. 作为准备分享会话的用户，我希望看到内容暴露风险并进行二次确认，从而避免意外公开代码、提示词或工具输出。

### 聊天与上下文

24. 作为日常使用者，我希望在活动栏侧边栏持续聊天，从而在编码时保持 Agent 可见。
25. 作为阅读长回复的用户，我希望把同一会话展开到编辑器标签页，从而获得更大的阅读与操作空间。
26. 作为在两种界面间切换的用户，我希望保持同一会话和滚动状态，从而不会产生重复会话或丢失上下文。
27. 作为选择代码后提问的用户，我希望当前选区自动成为可见上下文，从而减少复制粘贴。
28. 作为需要更多上下文的用户，我希望显式添加当前文件、多个文件、文件夹、Problems、Git Diff，以及插件从开始监听时捕获的命令输出或我粘贴的终端文本，从而准确控制发送内容且不误以为插件能读取任意终端历史。
29. 作为隐私敏感用户，我希望除选区外的编辑器内容不会被静默附加，从而知道模型实际接收了什么。
30. 作为熟悉 OpenCode 的用户，我希望完整使用动态加载的 `/` 命令，从而保留 CLI 工作流。
31. 作为使用自定义 Agent 的用户，我希望通过 `@` 搜索和提及 OpenCode Agent，从而调用已有配置。
32. 作为添加文件上下文的用户，我希望通过 `@` 模糊搜索文件和符号，从而快速引用工作区内容。
33. 作为高级用户，我希望在输入框使用 OpenCode 原生 Shell 命令能力，从而不离开当前会话。
34. 作为多模态模型用户，我希望拖拽或粘贴图片和截图，从而让 Agent 分析视觉信息。
35. 作为处理文档的用户，我希望添加 PDF 附件，从而让支持该模态的模型读取文档。
36. 作为模型能力不匹配的用户，我希望发送前看到附件不受支持的原因，从而避免静默失败。
37. 作为输入复杂提示的用户，我希望文本草稿和可重建上下文在界面切换与重新加载后保留；二进制附件则遵循明确的临时存储、过期清理和重启恢复规则，从而既减少丢失又不形成隐蔽的长期副本。

### 回复、工具与执行

38. 作为阅读回复的用户，我希望 Markdown、代码块、链接和差异内容清晰呈现，从而快速理解 Agent 输出。
39. 作为关注执行过程的用户，我希望看到简洁的工具时间线，从而知道 Agent 正在读取、搜索、执行或修改什么。
40. 作为需要排查问题的用户，我希望展开工具参数和完整输出，从而检查实际操作细节。
41. 作为查看长命令输出的用户，我希望默认折叠、复制或在内置终端中查看，从而避免聊天被日志淹没。
42. 作为希望理解推理的用户，我希望展开或收起 OpenCode 返回的思考内容，从而自行控制信息密度。
43. 作为不想阅读思考的用户，我希望默认只看到思考状态和摘要式入口，从而保持聊天简洁。
44. 作为任务执行者，我希望随时停止指定会话，从而终止不再需要或行为异常的任务。
45. 作为运行交互式程序的用户，我希望在插件内置的可折叠终端中输入内容，从而不被迫切换到外部终端。
46. 作为安全敏感用户，我希望区分 OpenCode 执行通道与插件辅助 PTY 通道，从而了解各自的权限和回退边界。
47. 作为使用子 Agent 的用户，我希望看到可展开的子任务卡片、状态和摘要，从而理解并行代理的工作进展。
48. 作为查看子 Agent 详情的用户，我希望进入对应子会话而不把全部内部消息铺进主时间线，从而兼顾可追踪性与可读性。
49. 作为按计划工作的用户，我希望看到实时 Todo 面板，从而掌握任务步骤和完成状态。
50. 作为关心成本的用户，我希望查看 Provider 实际返回的 Token、上下文占用与费用，从而管理使用成本。
51. 作为 Provider 不返回用量的用户，我希望看到明确的“未提供”状态，从而不会把估算值误认为真实账单。
52. 作为长会话用户，我希望查看上下文占用和压缩状态，从而知道何时发生上下文整理。
53. 作为希望控制压缩的用户，我希望按配置作用域开启或关闭 OpenCode 自动压缩并调整剪枝与预留量，从而匹配自己的工作流。

### 权限与变更审查

54. 作为安全敏感用户，我希望插件严格复用 OpenCode 权限判断，从而不会出现 CLI 与插件安全策略不一致。
55. 作为收到敏感工具请求的用户，我希望选择允许一次、本会话记住或拒绝，从而精细控制 Agent 行为。
56. 作为有多个并发任务的用户，我希望统一查看待处理权限请求及其会话来源，从而不会遗漏或误批。
57. 作为代码审查者，我希望授权、工具执行和结果审查是三个独立阶段，从而清楚区分风险许可与结果接受。
58. 作为审查 Agent 修改的用户，我希望查看文件列表、增删行统计和 VS Code 原生 Diff，从而理解所有变更。
59. 作为只接受部分结果的用户，我希望基于修改前、修改后和当前磁盘三份内容按文件或整体保留、回退变更，从而灵活处理 Agent 输出且不依赖 OpenCode 不存在的逐文件回退接口。
60. 作为已有未提交修改的用户，我希望回退只影响 Agent 产生的内容，从而保护任务开始前的工作。
61. 作为 Agent 修改与个人修改重叠的用户，我希望自动回退停止并打开三方 Diff，从而手动解决冲突而不丢失数据。
62. 作为 OpenCode 未提供完整 `FileDiff`、修改前内容或回退能力的用户，我希望插件降级为只读差异查看并明确说明原因，从而不会承诺无法证明安全的自动回退。

### 认证、模型与配置

63. 作为首次连接 Provider 的用户，我希望在插件内发起、跟踪并完成认证状态；浏览器 OAuth 可以安全打开系统浏览器，但不要求我使用外部终端，从而兼容 Provider 的真实认证约束。
64. 作为使用不同认证方案的用户，我希望认证界面根据 OpenCode 元数据动态生成，从而支持 API Key、OAuth、设备码及未来方案。
65. 作为安全敏感用户，我希望 Provider 凭据直接交给 OpenCode 保存；插件只把自身连接外部 Server 所需的认证信息保存在 VS Code 密钥存储中，从而不建立第二套 Provider 密钥库，也不把连接密码写入普通设置。
66. 作为多 Provider 用户，我希望只看到 OpenCode 实际连接和支持的 Provider 与模型，从而与 CLI 配置保持一致。
67. 作为每次任务需求不同的用户，我希望选择 Provider、模型、Variant 和 Agent，从而控制质量、速度和成本。
68. 作为使用自定义命令和 Agent 的用户，我希望插件动态读取 OpenCode 配置，从而新增配置无需等待插件升级。
69. 作为 MCP 用户，我希望查看 MCP Server 状态并通过插件管理官方 API 支持的配置，从而集中处理工具连接。
70. 作为配置用户，我希望在原生设置页管理默认模型、Agent、权限、压缩、MCP 和其他稳定配置，从而减少手工编辑 JSON。
71. 作为高级配置用户，我希望一键打开原始 OpenCode 配置文件，从而编辑插件界面未覆盖的复杂选项。
72. 作为有全局和项目配置的用户，我希望查看最终生效值和 OpenCode 规定的优先级，并仅在插件能够证明时显示字段的精确来源，从而不会把推测伪装成事实。
73. 作为修改配置的用户，我希望在本地且能够访问配置文件时明确选择全局或当前项目作用域；外部服务不支持作用域写入时显示只读或打开原始文件入口，从而不会静默改写错误层级。
74. 作为组织托管环境的用户，我希望被管理的配置显示为只读及其来源，从而理解为何无法覆盖。

## 实现决策

### 产品边界

- 产品专注 OpenCode，不做多 Agent CLI 通用外壳；内部保留可测试的后端边界，但不为其他后端牺牲 OpenCode 完整能力。
- 用户负责安装和升级 OpenCode CLI。插件负责发现、版本检查、自定义路径、能力探测和清晰的安装/升级指引。
- 插件不提供实时行内代码补全，聚焦会话式编码 Agent、任务执行、权限与变更审查。
- 正式支持 VS Code Desktop 的 Windows、macOS、Linux，以及 Remote SSH、WSL、Dev Containers；不支持 `vscode.dev` 浏览器版。
- 首版只正式测试 Microsoft VS Code，其他兼容编辑器不作承诺。

### 系统架构

- 可维护性是硬性验收要求：每个模块只承担一个清楚职责，通过小而稳定的接口形成深模块；禁止把 CLI、Server、会话、消息、事件、Webview 协议和界面渲染堆入同一代码文件。详细约束记录在开发规范中，并纳入每次代码审查。
- Extension Host 是可信协调层，负责进程生命周期、OpenCode 通信、VS Code API、文件与终端能力、诊断和安全策略。
- Webview 是非可信展示层，负责 React UI、用户输入和可序列化视图状态；不能直接访问 Node.js、文件系统或凭据。
- `OpenCodeRuntime` 是唯一的应用级测试接缝，对外只接收稳定的用户意图并发布归一化状态，不暴露 SDK、SSE、进程或内部模块细节。连接、协议、会话、写入仲裁和审查分别由内部深模块负责，避免把 Runtime 变成拥有大量功能方法的浅层总管。
- Server Manager 默认以随机本地端口和随机密码启动 `opencode serve`，验证健康状态与版本，并在 Extension Host 关闭时先请求中止本窗口发起的任务，再优雅终止插件拥有的进程；用户自行管理的外部 Server 永不由插件终止。
- Connection Topology 根据连接配置区分插件管理的本地服务、同文件系统的已有服务和不同文件系统的远程服务。非回环地址必须使用 HTTPS；需要明文协议的自管服务应先通过 SSH 隧道等方式映射为本机回环地址。连接认证信息存入 VS Code 密钥存储。无法证明路径可映射时，文件上下文、Diff、回退和 PTY 必须按能力降级。
- Protocol Compatibility 组合最低支持版本、运行时能力探测和 OpenAPI 契约结果，输出稳定的能力集合与降级原因；未知事件保留可诊断信息但不得让状态机崩溃。
- OpenCode Gateway 使用官方 `@opencode-ai/sdk` 与 Server API，不解析 TUI 文本或 ANSI 输出；所有命令、Agent、Provider、模型、权限、Diff、子会话和 Todo 都按服务端能力动态获取。
- Event Normalizer 将 SSE 初始快照与增量事件归一化为稳定的插件领域事件，并负责乱序、重复、断线重连和能力差异。
- Directory Router 始终以会话记录的初始目录路由请求和事件。UI 可以全局显示会话，但活动编辑器、当前工作区或另一窗口不得悄悄改变既有会话的根目录。
- Session Coordinator 管理当前窗口的单活动会话、统一状态与权限通知。切换会话前会中断本窗口发起的运行任务；OpenCode 的忙碌状态是外部客户端能否发送驱动操作的最终事实。
- View State Store 保存可重建的 UI 状态、文本草稿和用户偏好，不复制 OpenCode 消息历史、Provider 凭据或文件快照。剪贴板图片等不可重建附件只允许进入受控临时存储，并具有大小上限、过期时间、移除清理和启动清理。
- React Webview 在侧边栏和编辑器标签页复用同一组件树和状态协议，两者可以无损转移同一会话。
- Context Builder 负责把选区及用户显式选择的文件、目录、诊断、可合法获取的终端输出、Git Diff、图片和 PDF 转换为 OpenCode 原生消息 Part，并在发送前展示可见标签。终端上下文仅来自插件开始监听后的 Shell Integration 输出、插件拥有的 PTY 或用户粘贴文本，不读取任意既有滚动缓冲区。
- Permission Center 只呈现和响应 OpenCode 权限请求，不在客户端重新推断权限；统一支持允许一次、记住和拒绝。
- Change Review Engine 使用 OpenCode `FileDiff.before/after` 与当前磁盘内容建立可重建的变更账本。只读查看使用 VS Code Diff；逐文件操作执行三方合并并在落盘前重新校验当前内容；整条消息回退只有在能证明不会覆盖后续修改时才调用 OpenCode revert。插件禁止使用破坏性 Git 命令实现接受或回退。
- Embedded Terminal 使用插件管理的 PTY 与 Webview 终端组件处理确需 stdin 的交互流程。该通道与 OpenCode 工具执行明确区分，不伪装为受 OpenCode Snapshot 完整管理的操作。
- Authentication Center 根据 OpenCode Provider 认证元数据动态渲染 API Key、OAuth、设备码等流程，Provider 凭据直接交给 OpenCode 持久化。浏览器 OAuth 通过系统浏览器完成授权，远程或外部 Server 必须先验证回调可达性，否则改用设备码或明确失败。
- Configuration Center 展示最终生效配置和已知优先级，只在可靠数据存在时标注字段精确来源。Configuration Repository 仅在本地可访问配置文件时按用户选择编辑全局或项目 JSON/JSONC，并保留未知字段与注释；无法控制作用域的外部 Server 配置降级为只读。
- Restricted Mode Gateway 在未信任工作区阻止所有执行型意图、工作区文件读取、项目配置加载和工作区来源的可执行路径。若要展示历史，只能连接从中立目录启动的运行环境，并由 Extension Host 对允许的只读请求实施白名单；没有该条件时仅显示受限说明和健康状态。
- VS Code Integration 提供活动栏入口、编辑器标签页、命令面板、右键菜单、Problems、通知、Workspace Trust 和 Remote Extension Host 适配。
- Diagnostics 层使用结构化、内容脱敏的本地日志；内容遥测永久禁止，匿名崩溃与功能统计仅在用户主动同意后启用。

### 会话与目录语义

- OpenCode 是会话的唯一事实来源，插件显示并继续 CLI、桌面端或其他客户端创建的会话。
- UI 不按工作区锁定或隐藏会话。新会话使用活动文件所属工作区作为初始目录；无文件夹时必须显式选择目录。
- 跨目录能力及授权继续遵循 OpenCode 的 `external_directory` 等权限，不由插件扩大访问范围。
- 会话的初始目录是稳定身份的一部分。切换活动编辑器不改变它；跨目录访问走 OpenCode 权限，新根目录任务应新建会话。
- 切换会话前，插件中断本窗口发起且仍在运行或等待授权的当前会话；随后加载目标会话。界面呈现运行、跟随、等待授权、完成、失败和中断状态，不提供同项目写入排队。
- 关闭窗口时，插件先对本窗口发起且仍在运行的会话请求中止，然后释放订阅与 PTY，并终止该 Extension Host 启动的服务。外部服务进程不被终止。下次启动只恢复历史与状态，不自动继续执行。
- 插件不提供会话分支功能。历史消息不可原地修改；“重新发送”会把原提示追加到当前会话，“编辑后发送”会把修改后的提示追加到当前会话。两种操作都保留原始历史，且不会创建子会话。

### 交互与视觉

- 默认界面是活动栏侧边栏，并支持把同一会话展开为编辑器标签页。
- 消息时间线默认简洁：回复、思考摘要入口、工具状态和结果。思考、工具参数与完整输出均可独立展开或收起。
- `/` 命令、`@` Agent、文件/符号提及和 Shell 输入均由 OpenCode 动态能力驱动，不在插件中硬编码语义。
- 图片、截图和 PDF 支持拖拽、粘贴与选择；发送前按当前模型模态能力校验。文件 URI 可以重建，剪贴板二进制只在活动草稿的受控临时生命周期内保留；界面必须说明 Extension Host 重启后的恢复能力。
- 权限卡片负责执行前许可，工具卡片负责执行状态，变更中心负责执行后审查，三者保持明确分离。
- 子 Agent 以可展开任务卡片展示并可进入子会话；Todo 以持续可见的计划面板展示。
- 默认使用 VS Code 主题变量、字体和交互密度。品牌主色为天蓝色，用于关键操作、状态和品牌元素；高对比度模式优先于品牌颜色。
- 所有关键操作支持键盘导航、焦点可见、屏幕阅读器语义和减少动态效果偏好。
- 首发语言为简体中文和英文；模型回复、工具输出和配置值不自动翻译。

### 配置、认证与隐私

- Provider、模型、Variant、Agent、命令、MCP 和认证方式均从 OpenCode 获取，禁止维护硬编码 Provider 白名单。
- 插件内完成认证的发起、状态和结果交互，但浏览器 OAuth 可打开系统浏览器；不读取、复制或另行保存 Provider API Key，认证材料直接发往用户明确选择且通过连接安全检查的 OpenCode Server。
- 插件拥有两类不同秘密：Provider 凭据由 OpenCode 保存；连接外部 OpenCode Server 所需的密码或令牌由 VS Code 密钥存储保存。两者都不得进入 Webview 持久状态、普通设置、日志或遥测。
- 自动压缩使用 OpenCode 原生 `compaction.auto`，并展示 `prune` 与 `reserved`；插件不自行截断或总结历史。
- 配置编辑必须显示目标作用域；精确来源只有在能够证明时才显示，不能从合并结果反推。组织托管配置不可覆盖；项目配置与全局配置遵循 OpenCode 合并优先级。不同文件系统的外部服务没有可靠写入接口时只读展示。
- 内容零遥测。诊断日志默认本地、结构化且脱敏，导出前再次过滤敏感字段。

### 兼容与发布

- 兼容策略同时使用最低支持版本和运行时能力探测；缺少非核心能力时局部降级，核心协议不兼容时要求升级。
- 插件在未受信任工作区不能从工作区目录启动或配置 OpenCode，不能启动 Agent、读取工作区上下文、执行命令或修改文件。历史与有效配置只有在中立运行环境和后端只读请求白名单同时成立时才可查看，否则显示受限状态而不建立连接。
- 产品名称为 **OpenCode for VS Code — Community**，界面简称 **OpenCode for VS Code**，明显标注非官方社区客户端并使用独立天蓝色品牌视觉。
- 项目开源并采用 MIT License。
- 功能开发期间使用本地 VSIX 持续自用，不为发布时间压缩范围；全部目标功能完成并通过跨平台验证后再进入 Marketplace Pre-Release。

### 技术选型

- Extension Host：TypeScript、VS Code Extension API、esbuild。
- Webview：React、TypeScript、Zustand、Vite。
- UI 组件：轻量自建组件与可访问性原语，样式基于 VS Code Theme Tokens，不引入重型全局 UI 框架。
- OpenCode 集成：官方 `@opencode-ai/sdk`、OpenCode Server API、SSE。
- 内置终端：Webview 终端组件加 Extension Host PTY，按目标平台打包和验证原生依赖。
- 国际化：编译期键值资源与运行时语言选择，覆盖 Extension Host 和 Webview 文案。

## 测试决策

- 好测试只观察外部行为，不断言私有函数、React 内部状态或 SDK 调用顺序等实现细节。
- 主要测试接缝是 `OpenCodeRuntime`：测试向它发送与真实 UI 相同的用户意图，并通过模拟 OpenCode Server/SSE 观察归一化状态、协议请求、并发、权限、恢复与文件审查结果。
- `OpenCodeRuntime` 的公开测试协议保持小而稳定：用户意图输入、归一化状态订阅和明确结果。内部模块通常通过该最高接缝验证；只有三方合并、路径映射等高组合复杂度纯逻辑需要补充窄接口属性测试。
- 模拟 Server 必须由 OpenCode OpenAPI/SDK 类型约束，覆盖健康检查、会话、消息流、权限、Diff、revert、Provider 认证、配置、MCP、子会话、Todo 和错误响应。
- 协议契约测试覆盖最低支持版本和代表性新版本、能力探测、未知事件、事件重复、乱序、断线重连、服务重启、部分 API 缺失、版本不兼容和同一会话多客户端竞争。
- 并发测试覆盖不同项目并行、同项目写入排队、隔离工作树并行、窗口租约失效、未知外部客户端忙碌、审查期间外部编辑和关闭窗口释放租约。
- Change Review 测试以 `before`、`after`、`current` 为三方输入，覆盖干净工作区、已有用户修改、同文件不重叠修改、同区域冲突、新建/删除/重命名文件、换行符与编码、能力缺失和回退失败，断言永不覆盖任务开始前或 Agent 完成后的用户内容。
- Authentication 与 Configuration 测试覆盖动态认证方式、凭据不进入插件存储、全局/项目作用域、托管只读配置和能力降级。
- Context Builder 测试覆盖选区自动附加、显式上下文、二进制附件临时生命周期、模型模态拒绝、Shell Integration 监听边界、Remote URI 与路径规范化。
- Embedded Terminal 测试覆盖 PTY 输入输出、调整尺寸、退出、取消、远程环境和与 OpenCode 工具通道的视觉区分。
- Webview 测试从可访问角色和用户操作验证双形态聊天、思考折叠、工具卡片、授权、Diff 入口、会话切换、草稿保持和键盘导航。
- Extension Host 集成测试验证命令注册、Workspace Trust、生命周期、通知、URI/文件操作和侧边栏到编辑器标签页迁移。
- 连接拓扑测试覆盖回环与非回环、HTTP 拒绝、HTTPS、连接密钥存储、同文件系统、路径映射缺失、不同文件系统能力降级、外部服务不被终止以及远程 OAuth 回调不可达。
- 性能测试从首次消息时间线实现开始覆盖长会话虚拟化、批量事件合并、工具输出大小上限和慢 Webview 背压，不把这些结构性约束推迟到发布任务。
- 使用真实 OpenCode CLI 的无付费模型兼容测试验证进程启动、健康检查、OpenAPI 能力和基本会话持久化。
- 打包后的 VSIX 在 Windows、macOS、Linux 上执行冒烟测试，并人工覆盖 Remote SSH、WSL、Dev Containers、亮/暗/高对比度主题和中英双语。
- 当前仓库没有既有实现或测试先例；测试结构将以单一高层接缝为原则建立，避免为每个内部模块创建脆弱的重复测试套件。

## 不在范围内

- 支持 Claude Code、Codex 或其他 Agent CLI 后端。
- GitHub Copilot 风格的实时行内代码补全。
- 自动下载、安装、捆绑或升级 OpenCode CLI。
- 解析或嵌入 OpenCode TUI 的终端文本界面。
- 在插件内维护独立的聊天记录、凭据、权限规则或文件快照数据库。
- 保证阻止 OpenCode TUI、桌面端或任意第三方客户端驱动同一会话；插件只协调自身实例，并以 OpenCode 忙碌状态处理未知客户端。
- 在没有路径映射或同文件系统证明的外部 Server 上执行文件上下文、Diff、回退或插件 PTY。
- 读取插件开始监听之前的任意 VS Code 终端滚动历史。
- 保证所有 OAuth 都能在 Webview 内完成；需要浏览器的 Provider 使用系统浏览器，设备码流程仍可完全在插件中引导。
- 在 OpenCode 不提供完整修改前后内容且当前文件已经变化时承诺安全的逐文件自动回退。
- 支持 `vscode.dev`、浏览器 Extension Host 或移动端编辑器。
- 正式承诺 Cursor、Windsurf、VSCodium 等衍生编辑器兼容性。
- VS Code 关闭后继续运行任务的常驻守护进程。
- 打开工作区或恢复会话时自动继续中断任务。
- 在未受信任工作区运行 Agent 或读取工作区内容。
- 默认将整个工作区、当前文件或敏感内容静默发送给模型。
- 通过破坏性 Git 命令回退 Agent 修改。
- 将外部终端作为认证或交互式命令的必需步骤；系统浏览器不属于外部终端。
- 在完整功能和稳定性目标达成前公开发布 Marketplace 版本。

## 补充说明

- OpenCode Server 和 SDK 仍在快速演进。实现应以能力探测、归一化领域事件和契约测试隔离上游变化。
- “完整审查”依赖 OpenCode 返回可用的 `FileDiff.before/after`，并要求写入前重新读取当前磁盘内容。OpenCode 原生 Snapshot/revert 只用于能够证明安全的整条消息回退；能力缺失时必须降低为只读差异查看。
- 插件不协调不同窗口之间的项目写入。未知客户端始终按 OpenCode 报告的忙碌状态进入保守跟随模式。
- 不同文件系统上的外部 Server 是能力受限模式，而不是默认完整模式。只有明确路径映射并通过读写探测后才能逐项启用文件能力。
- 辅助 PTY 是为协议缺少通用 stdin 时提供的插件内体验，不应绕过或伪造 OpenCode 权限事件。
- 分享、远程 Server 与 Provider 认证都可能暴露敏感内容，所有相关界面必须显示目标、范围与风险。
- 需求与架构先于实现；开发以可持续自用为反馈循环，发现问题后更新本文档和后续任务，而不是通过一次性大版本冻结错误假设。
